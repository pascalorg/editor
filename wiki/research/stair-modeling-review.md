# Stair modeling review

Research date: 2026-10-05. Scope: Pascal's stair and stair-segment nodes, core rise/support/opening logic, 3D rendering, plan representation, inspectors, creation tools, agent operations, and IFC export. This records the original research and implementation sequence. Implementation is tracked in [stair implementation progress](stair-implementation-progress.md).

## Recommendation

Start with one resolved stair layout in core and correct arrival heights, counts, and editing parity. Then add constraint-based sizing and headroom diagnostics. Construction details and better creation workflows should build on those calculations.

Keep the existing stair/flight/landing graph. It already supports useful semantic editing and aligns with BIM decomposition. Replace the repeated layout calculations and divergent presentation rules, rather than replacing stairs with arbitrary meshes.

## Existing strengths

- Straight stairs chain flights and landings with front/left/right attachments. L/U arrangements can already be assembled manually.
- Curved and spiral stairs have parametric radii, widths, sweep, and steps. Spirals have optional column, supports, and integrated top landing.
- Rise can follow a destination level or same-level deck. Floor support and destination surface elevations participate in the calculation.
- Core synchronizes slab/ceiling cuts and tracks ownership, preserves authored holes, and previews openings during live edits.
- Registry capabilities cover selection, placement, snapping, duplication, painting, floor plans, and editing handles. Live geometry reads transient overrides.
- Straight bodies are merged outside segment editing; rebuilds are throttled. Tread/body geometry has metre-scale UVs.
- Plans already provide UP/DN, breaks, riser/tread/width notes, and railing notes. IFC export already aggregates a stair assembly.

## Findings in the current implementation

These were the source-derived findings at the start of the work. Dependencies have since been restored, and each implemented slice has received independent verification.

| Priority | Finding and observable consequence | Code evidence | Proposed change |
|---|---|---|---|
| First | **Spiral arrival depends on tread thickness.** Spiral tread `i` starts at `i * rise/count` and its top adds thickness. The last tread reaches `rise - rise/count + thickness`, rather than necessarily reaching the destination. With 3 m rise, 15 steps and 50 mm thickness, its top is 2.85 m. The first rise is also thickness rather than the nominal riser height. | `packages/nodes/src/stair/renderer.tsx`, `CurvedStairBody`; integrated landing thickness also derives from this last tread top. | Define walking-surface elevations first and put thickness below them. Explicitly define whether the destination is a final tread or a landing. Account for open-riser gaps independently. |
| First | **Custom parent rise and existing straight flights have different authority.** The parent panel changes only `totalRise`. `syncStairRises` deliberately skips detached stairs with an explicit rise, and rendering uses child heights. A custom-rise edit can therefore change the displayed resolved rise without changing the stair body. | `packages/nodes/src/stair/panel.tsx`; `packages/core/src/systems/stair/stair-rise-query.ts`; `packages/viewer/src/systems/stair/stair-system.tsx`, `updateMergedStairGeometry`. | A parent-rise command must redistribute child heights atomically; per-flight edits must update the aggregate. Preserve deliberately measured flight geometry rather than making a background synchronizer overwrite it indiscriminately. |
| First | **2D and 3D disagree about step counts and multi-turn sweeps.** 3D permits two curved/spiral steps; plan rendering and notes use minimum counts of four/six. Plan helpers clamp sweep to just under one turn, and documentation uses the clamped sweep to calculate tread depth. A 400° spiral is annotated using approximately 360°; 720° produces roughly half the correct centerline arc going. | `packages/nodes/src/stair/{renderer,floorplan,documentation}.tsx/ts`; `packages/editor/src/lib/floorplan/stairs.ts`. | Keep the full semantic sweep for calculations. Derive plan graphics by projecting the actual treads and applying view-specific visibility, without modifying their dimensions or count. |
| First | **Paint changes can disappear when selecting straight segments.** The parent renderer resolves paint slots; the segment renderer uses the legacy material helper, which ignores parent slots. Segment meshes also lack the parent's slot hit metadata. The merged body also does not use segment material overrides, whereas segment rendering does. | `packages/nodes/src/stair/renderer.tsx`; `packages/nodes/src/stair-segment/renderer.tsx`; `packages/viewer/src/systems/stair/stair-materials.ts`; `packages/nodes/src/stair/paint.ts`. | Resolve identical effective slots and material overrides in merged and editable views. Give editable surfaces identical slot metadata and ownership rules. |
| Next | **Rise following does not ensure uniform risers across flights.** Heights scale proportionally to existing flight heights, independent of step counts. Flights with different height/count ratios retain unequal risers after synchronization. | `packages/core/src/systems/stair/stair-rise-query.ts`, `syncStairRises`. | For designed stairs, allocate integer risers across flights and use one resulting riser height. Preserve surveyed irregular stairs and report the differences. |
| Next | **Openings are heuristics, not a headroom solution.** Straight depth is the maximum of ten tread depths, 80% of the run, and 3 m, limited to the run; curved cuts cover 80% of the sweep; spiral cuts use a full circle. These do not measure clearance to actual overhead surfaces. | `packages/core/src/systems/stair/stair-opening-sync.ts`; `packages/core/src/agent-operations/verify-scene.ts` checks footprint/wall/opening conditions, but does not calculate stair headroom. | Calculate a clearance envelope above tread/landing walking surfaces and compare with slabs, ceilings, upper flights, and other overhead geometry. Preview the required cut and obstruction diagnostics. |
| Next | **Creation paths have different sizing defaults.** Interactive creation seeds ten steps; MCP defaults to fourteen; mezzanine planning derives count from a 250 mm nominal rise. The interactive tool follows storey height without adapting step count or run to a comfort target. | `packages/editor/src/components/tools/stair/{stair-defaults,stair-tool}.ts/tsx`; `packages/mcp/src/tools/construction-tools.ts`; `packages/core/src/commands/structure/plan-mezzanine-stair.ts`. | One core creation planner should choose counts/run from target dimensions and selected rules, and return alternatives if the available footprint is insufficient. |
| Next | **Railing controls overstate supported variants.** The panel exposes all four styles for every stair type, but non-baluster guard construction only runs for straight stairs. Curved/spiral rails connect posts with straight bars, and their paths do not extend around the integrated spiral landing. | `packages/nodes/src/stair/{panel,renderer}.tsx`, `StairRailings`. | Make available controls reflect implemented styles. Derive continuous rail/guard paths through flights and exposed landing edges, with distinct graspable handrail and guard settings. |
| Later | **Construction is under-specified.** Straight bodies support solid fill or a stepped top over a sloped underside; curved bodies use individual wedges. There are no explicit tread nosing, separate riser, straight stringer, or finish-layer parameters. One thickness field carries different meanings across variants. | Stair schemas; `generateStairSegmentGeometry`; `CurvedStairBody`. | Add explicit construction modes and detail dimensions: solid/waist slab, open treads with side or central stringers, closed risers, nosing, and tread finish. Implement useful modes in successive slices. |
| Later | **IFC export loses stair semantics.** No `Pset_StairFlightCommon` is emitted; stair aggregation uses the same flight class for every stair-segment, including landings. Parent merged geometry can also become a generic flight member. Null legacy count/dimension attributes are appropriate for IFC4 and are not themselves the defect. | `packages/ifc-converter/src/export/scene-to-ifc.ts`, `STAIR_FLIGHT` and stair `aggregateParts` call. | Export resolved flights as IfcStairFlight with common properties; represent landings as IfcSlab LANDING and railings separately where appropriate. Preserve assembly identity and source geometry on import. |

Additional maintenance issues: chain-transform logic is repeated in core footprints, core floor-support footprints, viewer geometry, node railings, and editor floor plans. `generateStairRailingGeometry` in the viewer has no callers. Inspector limits differ between handles, parametric descriptors, and custom panels, including arbitrary maxima such as 30/32 steps and 10 m width. Consolidating these paths reduces future drift and addresses E-008.

## What established tools do

**Solve dimensions together.** Revit's calculator takes minimum tread depth, maximum riser height, and a rise/tread relationship. Pascal should offer a sizing solver, actual riser/going readouts, and explicit locked inputs. A comfort relationship is a design target, not universal code compliance. [Autodesk stair calculator](https://help.autodesk.com/cloudhelp/2022/ENU/RevitLT-ArchDes/files/GUID-4E763B5A-1FFF-4084-BFAC-B587FEB01B3D.htm), [Autodesk dimension editing](https://help.autodesk.com/cloudhelp/2025/ENU/RevitLT-ArchDes/files/GUID-7EA40FA9-3128-45B2-B794-8E33036E9D9B.htm).

**Separate layout from construction and annotation.** Revit distinguishes stair, run, landing, support, path, and tread/riser numbering properties. Pascal's existing graph is a useful starting point, but geometry and annotation should consume the same resolved data. [Autodesk stair properties](https://help.autodesk.com/cloudhelp/2026/ENU/Revit-ArchDesign/files/GUID-7EBB3572-176C-4AC4-A841-48CCA7E742F5.htm).

**Offer alternatives when a design does not fit.** Archicad's Stair Solver presents alternative arrangements when a stair conflicts with constraints. Pascal can start with a few deterministic straight/L/U candidates and explain which dimension must change. [Graphisoft Stair Tool](https://helpcenter.graphisoft.com/user-guide/76585/).

**Model the walking line and headroom explicitly.** Archicad distinguishes the boundary, baseline, and walking line, and provides headroom settings with vertical or perpendicular measurement. Pascal should label its current curved tread measure as centerline going and make the actual measurement line an explicit rule when checking winders or spirals. [Graphisoft graphical editing](https://help.graphisoft.com/AC/28/INT/_AC28_Help/040_ElementsVB/040_ElementsVB-180.htm), [Graphisoft rules and standards](https://helpcenter.graphisoft.com/user-guide/88684/).

**Keep quantities semantic.** IFC provides separate tread and riser quantities. Pascal currently uses `stepCount` as both the visible-step concept and the riser-count annotation. Define start/end conditions before changing the persisted convention; do not simply subtract one tread from all existing scenes. [buildingSMART NumberOfTreads](https://ifc43-docs.standards.buildingsmart.org/IFC/RELEASE/IFC4x3/HTML/property/NumberOfTreads.htm).

Revit explicitly supports beginning and ending a run with a riser. This is why riser count and manufactured tread count need distinct meanings. Its spiral tool also supports sweeps beyond one revolution. [Autodesk run instance properties](https://help.autodesk.com/cloudhelp/2021/ENU/Revit-ArchDesign/files/GUID-22EC1748-A525-43BB-A45E-97D104CF303B.htm), [Autodesk full-step spiral](https://help.autodesk.com/cloudhelp/2020/ENU/Revit-Model/files/GUID-F521015D-1703-48EA-847D-184E6C277BDB.htm).

**Use construction parameters without moving the walking surface.** FreeCAD's stair source exposes tread/riser thickness, nosing, enforced versus derived dimensions, and outlines for railings. Archicad supports monolithic, beam, cantilevered, and stringer structures. These are references for a useful construction vocabulary, rather than a reason to implement all variants at once. [FreeCAD ArchStairs source](https://github.com/FreeCAD/FreeCAD/blob/main/src/Mod/BIM/ArchStairs.py), [Graphisoft stair structures](https://helpcenter.graphisoft.com/user-guide/76598/).

IFC's common stair-flight properties include separate counts, riser height, going at a walking line, inner-side going, nosing, headroom, and waist thickness. The older flight entity attributes are deprecated; use the property set appropriate to Pascal's IFC4 export target. Landings belong to the slab class within the stair assembly. [buildingSMART flight definition](https://standards.buildingsmart.org/IFC/RELEASE/IFC4_3/HTML/lexical/IfcStairFlight.htm), [buildingSMART flight properties](https://standards.buildingsmart.org/IFC/RELEASE/IFC4_3/HTML/lexical/Pset_StairFlightCommon.htm), [buildingSMART stair decomposition](https://standards.buildingsmart.org/IFC/RELEASE/IFC4_3/HTML/lexical/IfcStair.htm).

For turning stairs, equal-angle wedges and equal-going winders are different designs. The latter requires solving tread boundaries against the walking line; it cannot be obtained merely by rotating the existing rectangular flights. Treat it as an explicit later capability. [Graphisoft turning types](https://help.graphisoft.com/AC/29/INT/_AC29_Help/040_ElementsVB/040_ElementsVB-181.htm).

## Proposed implementation sequence

1. **Correctness and shared layout.** Add pure core resolution for segment transforms, tread/landing elevations, actual counts, full sweep, entry/arrival frames, and footprints. Consume it in both views, opening generation, and measurements. Fix spiral elevation, parent custom-rise commands, and selected/merged paint parity. Remove unused railing generation and repeated transform implementations as their consumers move over.
2. **Sizing and diagnostics.** A core planner derives integer risers from rise and target limits, distributes them across flights, and reports actual going, slope, and uniformity. Add readouts and repair actions in the panel. Make interactive, mezzanine, and agent creation share it. Separate mathematical invalidity from profile-dependent design warnings; preserve existing measured irregular stairs.
3. **Headroom and openings.** Generate and query a walking clearance envelope. Include lower/upper flights and landings, both signs of spiral sweep, and repeated turns. Keep existing opening ownership, authored-hole preservation, preview, and undo behavior; use the computed required region to improve cuts.
4. **Usable layout and construction.** Add straight/L/U presets, automatic landing sizing, clockwise/counterclockwise controls, a selected-walking-line display, and fit alternatives. Add construction modes, nosing/riser detail, continuous railing transitions, and optional glass/metal styles after the layout is reliable.
5. **Portable semantics and fidelity.** Carry the resolved quantities into agent responses, plan notes, and IFC. Benchmark representative stair populations before changing batching; retain dirty queues, live overrides, registry dispatch, and portable GLB/USDZ/baked-viewer behavior.

A new path-driven stair schema, arbitrary curved/winder segments, and repeated multi-storey stairs are useful later extensions. They are not prerequisites for fixing today's behavior.

## First slice acceptance criteria

- Spiral walking-surface elevations are independent of tread thickness and match the declared start/end convention; integrated landings meet their intended destination.
- Editing parent rise and a child height has defined, atomic effects on the graph and produces one undo step.
- Both views, annotations, and headless measurements agree on counts, arrival, and positive/negative multi-turn sweep.
- Paint and segment material overrides survive selection changes and export.
- Old scene fixtures retain their intended geometry through an explicit load/migration path when persisted meanings change (E-003). New defaults do not silently redesign existing stairs.
- Verify exported observable geometry/quantities and command results through package exports, in existing feature test files (T-001). Cover differing flight widths/counts, raised support slabs, decks, zero/invalid rise, two-step curves, thin/thick spiral treads, and integrated landings.

## Verification

Dependencies were restored with the frozen lockfile. Focused tests, independent public API probes, mounted renderer checks, and actual GPU/browser checks now cover the implemented slices. See the [verification ledger](stair-implementation-progress.md) for approved slices and final repository results.

Stair-flight export uses IFC4 ADD2 property names and types, including `NumberOfRiser` (singular), and measured values rather than design targets. Unknown quantities are omitted. [IFC4 flight properties](https://standards.buildingsmart.org/IFC/RELEASE/IFC4/ADD2/HTML/schema/ifcsharedbldgelements/pset/pset_stairflightcommon.htm), [IFC4 landing slab classification](https://standards.buildingsmart.org/IFC/RELEASE/IFC4/ADD2/HTML/schema/ifcsharedbldgelements/lexical/ifcslabtypeenum.htm).

Headroom coverage includes slabs, ceilings, and stair bodies. Arbitrary furniture, roof and imported-mesh obstacles are outside this query. Design targets are adjustable design guidance, not jurisdiction-specific compliance certification. Detail budgets refuse excessive geometry explicitly and preserve entered dimensions. Existing construction and railing layouts remain the default until an explicit edit selects the new features.
