# Agent surfaces

*Parity between the MCP server, the hosted AI chat, and the agent knowledge Pascal publishes.*

Applies to: `packages/mcp/**`, `skills/**`, and the scene operations and tool contracts in `packages/core/src/**` that agents call.

Pascal has two agent surfaces: the MCP server in this repo, used by external agents (Claude Code, Codex, …), and the AI chat of the hosted editor, whose loop lives in the hosted product. Both drive the same scene. What agents know about building in Pascal travels with them as the `pascal-3d` skill (`skills/pascal-3d/`) and the `pascal://agent-guide` resource. Treat these as **three presentations of the same capabilities** — the same default expectation as [2D ↔ 3D behavioral parity](tools.md).

## The rule

- **Capability parity.** A scene capability available to one surface's agent is available to the other's. The *mechanism* may differ (a server-side MCP handler vs a client-side chat executor); the *contract* must not: same name or a recorded alias, same input schema, same meaning in the description.
- **Same change.** When you add or change a capability on one surface, port it to the other in the same change, or write down why it genuinely doesn't apply (PR description and the parity map).
- **Operations live once.** A new capability is a core operation over `SceneApi` (`createSceneApi(store)`); each surface only adapts inputs and outputs. Never implement the same scene edit twice.
- **Rules live in the operation, not the loop.** A refusal or diagnostic that exists only in one surface's prompt or step logic is not enforced for the other surface's agents. Put realism refusals and `check`-style diagnostics where both surfaces execute them.
- **Knowledge parity.** A lesson that changes how an agent should build — a realism rule, a tool-choice rule, a known pitfall — is added to the published guide (skill references, agent guide) in the same change that teaches it to the chat, worded for any agent.
- **Agent first, by hand second.** Pascal is built agent-first. When a person could do by hand what an agent tool does, offer that alternative, in the same change or as a follow-up, reading the same core rule; it never blocks an agent tool from shipping. Example: `place_items` refuses a floor item in a door's clearance or too large for its room (`blocks_door`, `too_large_for_room`), and the editor's item tool warns about the same placement while the item is placed or moved, from the same check (`floorItemFit` in `core/building`).

### Parity by layer

A tool has three layers, and only the last one may differ between surfaces:

1. **Contract** — name, description, input schema — one definition in `@pascal-app/core/agent-tools` (a plugin's tool: in the plugin, see [Plugin tools](#plugin-tools)), registered by the MCP and defined by the chat from the same object. Kept zod-only: the chat declares tools inside a sandbox that rejects Node-dependent packages (`contracts-purity.test.ts`).
2. **Operation** — validation, defaults, clamping, refusals, the nodes to create — one pure function in core (`planWallOpening`, `verifyScene`, `duplicateLevel`…).
3. **Executor** — applying to a store (the chat's live store, the MCP's bridge) and the result envelope (live sync, persistence). Surface context resolves here too: "the active floor" is what the person is viewing in the chat, or in a page that hosts the MCP in-page (its `SceneOperations` lends it as `activeLevelId`, as the hosted Architect's does); the remote MCP has no view, and an operation that names no level reads the lowest storey there. An edit that reads construction the host derives (re-derived rooms, auto ceilings, floor plates — the room and floor tools) returns `afterReconcile`; both hosts run it through `applyAgentOutcome` with their own reconciler, in one undo step.

**The editor is the reference.** What a person can do by hand is what an agent may do: the operation reuses the editor tool's own rules (for openings: `clampDoorToWall`, `clampWindowToWall`, `findWallChildOverlap`, no openings on curved walls, overlap allowed only with force — the editor's Alt; a window style only on a Fixed window, as the panel offers it, one entry per look: `picture` is accepted as an alias of `single`). An agent-only guard is the exception, kept only when it is sane and worth giving the editor too.

**Refusals are answers.** An operation that cannot do what was asked throws `AgentRefusal(code, message, details)` — "Wall wall_a is 0.80 m long, too short for a 0.90 m door." Both surfaces return `{ error, code, ...details }`; the code is stable and counted (per thread, per week), and the message says what would work.

**Tests follow the layers.** A tool's edge cases are written first as one table (e.g. `building/__fixtures__/wall-opening-cases.ts`, or the shared `agent-operations/__fixtures__/cases.ts`) and run by three runners: the core operation (`operations.test.ts`), the MCP tool through a real client (`shared-tools.test.ts`), the chat executor on the real store. A change that makes one layer disagree fails.

**Wall finish readback is intent and base-chain provenance, not visual verification.** `get_zones` exposes persisted `wallMaterial` (string, or `null` when absent) and `wallOverrides` (`{ wallId, face, finish }` records, or `[]` when absent). `get_walls` and the walls in `get_level_summary` expose `wallFaceChains: { a, b }` through the shared `resolveWallFaceChain`: each face is a slot `ref`, a `legacy` inline spec, or a `default` fallback ref. Room overrides/defaults and face paint regions are separate layers; exterior assembly cladding, dangling refs, loading and visibility can also change the final appearance. A chosen white or default-matching ref is legitimate, and absence alone is not a defect or a requirement to paint. `get_node` retains the full detailed state.

## Adding a tool to both surfaces

A tool is written once and registered twice; never build the same tool separately for the chat and the MCP.

1. **Contract** in `packages/core/src/agent-tools/<area>.ts`: `{ name, title, description, input }`, zod only, and added to `AGENT_TOOL_CONTRACTS` (`agent-tools/index.ts`). The description is what both agents read: say what it does, its defaults, and its refusal codes. Every length and angle is `measurement(kind, unit)` in the unit the field states, and a roof pitch is `roofPitch('deg')` (or `'twelfths'`): a bare number keeps that unit, text in any unit is converted. A default goes in their `default` option, which states it in the description (a field that converts loses its JSON Schema `default`). Coordinates (x, z, points, rectangles), fractions and counts stay numbers; `agent-tools/notation.test.ts` fails on any other bare number and on a default the model is not shown, through `bareNumberPaths()` and `unshownDefaultPaths()` (`notation-inventory.ts`), which a plugin's notation test runs over its own contracts.
2. **Operation** in `packages/core/src/agent-operations/`: a pure function over the scene's nodes that returns `{ result, changes }` and refuses with `refuse(code, message, details)`; registered by tool name in `AGENT_OPERATIONS`. It selects what it reads (`queryNodes`, `orderedChildIds`) rather than enumerating `nodes`, so it runs precisely on a detached scene ([Computing off the live scene](#computing-off-the-live-scene)).
3. **Cases** in the shared fixture table, written failing first; the core and MCP runners pick them up.
4. **MCP**: an entry in `SHARED_TOOLS` (`packages/mcp/src/tools/shared-tools.ts`) with its annotations and output schema; the annotation policy (`scripts/openai-tool-annotation-policy.ts`) and `plugin-evals/tool-annotation-justifications.json` list it.
5. **Hosted chat**: the hosted repo defines its chat tool from the same contract and runs the same operation through its shared-tool executor; its `agent-surface-parity.test.ts` checks that the two surfaces' name, description and input schema match.
6. **By hand**, where possible: offer the editor's alternative, in the same change or as a follow-up. It never holds the tool back (agent first).
7. **Knowledge**: the `pascal-3d` skill, the agent guide (`pascal://agent-guide`) and the MCP README's tool table.

A tool that needs something only a host has keeps the same contract and operation; the host passes the missing piece to `createPascalMcpServer`. Without a renderer (`sceneViews`) or a script runtime (`geometryScripts`) the tool still exists and answers with a code (`view_unavailable`, `scripts_unavailable`); without a `catalog` the item tools draw from a small built-in list; hosted service tools are registered only with a `services` executor.

## Plugin tools

A plugin's tools keep the three layers; the plugin owns the first two instead of core (E-016). The contract is in its `./agent-tools` export, a `PluginAgentTools` of `PluginAgentTool`s (an `AgentToolContract` plus where it runs), zod only under the same purity rule. The operation of each `runsIn: 'operation'` tool is in its `./agent-operations` export, an `AgentOperations`. The executor is the host's. Both surfaces register from those same objects:

- **MCP**: `registerOperationTool(server, operations, { contract, operation, annotations })` from `@pascal-app/mcp/tools/shared-tools`, the runner of the shared tools: parse, plan, apply in one history step, `achieved`, the persistence envelope, refusals as `{ error, code }`. A `runsIn: 'editor'` tool needs an editor tab: the host routes it to one, as `view_scene` does, or refuses with a code.
- **Hosted chat**: the same contract defines the chat tool; `'operation'` tools run on the live store through its shared-tool executor, `'editor'` tools through the plugin's `PluginChatExtension.execute`.

Beyond the rules above:

- **Offered by the host.** A plugin's tools are offered only where the plugin is installed and the host's policy allows. A client's list of tools, or its claim that a plugin is installed, is never trusted.
- **Annotations from the host.** The host classifies each tool from its own review and registers it with its own annotations; a contract's `annotations` are the plugin's hints and never decide a write scope, a retry or an approval. A tool the host has not classified is not registered.
- **Versioned.** `PluginAgentTools.version` is the revision of the plugin's contracts; a host that runs long turns pins the revision a turn was offered.
- **Exceptions are recorded.** `chatOnly` is a request, honoured only as a reviewed exception to capability parity, written down like any other.
- **One name each.** A plugin tool's name collides with no core tool and no other plugin's; prefix it with the plugin.
- **Tests follow the layers.** The plugin's edge cases as one table, run against its operation and through `registerOperationTool` with a real client; `shared-tools.test.ts` does this for a synthetic plugin.

## Computing off the live scene

A host may run any shared operation, or a whole MCP bridge, on a **detached scene** instead of the live store (`@pascal-app/core/runtime`, [scene runtime](scene-runtime.md)): the same contract and operation, computed on a copy opened from a canonical snapshot, with deterministic ids (`effectIds`) and a record of what it read. The result is a complete field-level patch, applied to the live scene with `applyPatchWithDependencies` only if nothing it read has changed, or refused with what changed. Both surfaces keep one implementation:

- **Hosted chat**: `scene.execute(operation, input, context)`, or `applyAgentOutcome(op(scene.reader().nodes, …), scene.host())`.
- **MCP**: `new SceneBridge({ runtime: scene })`; every registered tool then reads and writes the detached scene. The shared-tool runner plans each operation inside the scene's scope (`runInScene`), so its ids are the scene's.

Derived construction settles inside the computation (`reconcileDocument`: rooms, stair rises and openings, roof elevation), so the patch is complete and applying it gives the editor's systems nothing more to write. The comparison contract (`runtime/fixture-parity.test.ts`) runs every shared fixture detached and live and requires identical patches.

## What stays surface-specific

Hosted service tools have public contracts in `core/agent-tools` and a shared request operation in `core/agent-operations`. A host opts into them with `createPascalMcpServer({ services })` or `registerHostedServiceTools`. Without that executor, the open-source server exposes its local scene tools only. Tool arguments carry project/plugin references and an approved credit ceiling; the host supplies verified identity and enforces access, billing and retained-result ownership. Provider selection, workflow prompts and orchestration belong to the host. Public discovery includes only the released contract inventory.

- **Loop control** — step caps, progress ledgers, prompt injection. The chat owns its loop; MCP clients own theirs.
- **Session and file operations** of the MCP (scenes, units, templates, export) have no chat counterpart unless the chat needs them.
- **UI-bound chat tools** (current selection, clarification questions) get an MCP counterpart only when external agents need the same information.

## Tells that parity is broken

- A tool exists on one surface with no entry in the parity map.
- Two tools share a concept but not a schema — e.g. a length that accepts `"6 ft"` on one surface only.
- An agent on one surface hand-builds, through `apply_patch`, what the other surface does in one operation.
- A chat prompt rule has no counterpart in the agent guide, or a guide rule contradicts a tool description (`apply_patch` described as "batch-first is the default" while the skill says to prefer semantic tools).

## Enforcement

- `@pascal-app/core/agent-tools` holds the shared contracts; the hosted repo's `agent-surface-parity.test.ts` fails when a shared tool's name, description or input schema differs between the MCP and the chat. Tools still defined twice are tracked in its tool-surface alignment plan.
- `review-architecture` loads this page for changes under `packages/mcp/**` and `skills/**`.

**A tool retires into its replacement**, once the replacement covers every case it served (a case table in `agent-operations/__fixtures__`, run by the three runners). The MCP lists it no more and still answers it: `RETIRED_MCP_TOOLS` in `core/agent-tools` names the replacement and how to use it, and a call to the name gets `{ error, code: 'tool_retired', replacement }` (`tools/retired-tools.ts`), where the SDK would answer an unknown name. The hosted product answers the same names on its own surfaces from the same map.

## Looking at the scene: `view_scene`

One contract (`viewSceneTool`) and one plan (`sceneViewPlan` in `core/agent-operations`): the plan turns the request (a target, a side or an exact eye, a projection, a photo's camera) into a camera pose and an image size, and, when a photo region is given, a crop of the photo to return beside the view. Only the rendering differs by surface:

- **Hosted chat**: the editor in the same page renders the pose.
- **MCP**: the server has no renderer. It asks the host's `sceneViews` (a `SceneViewHost`, passed to `createPascalMcpServer`) for a capture of the active project. The hosted Pascal app answers through the person's editor tab open on that project, as a screenshot job the tab runs; with no tab open the call is refused `editor_tab_required` with the editor link, with the tab in the background `editor_tab_hidden`, so the agent asks the person to bring it forward, and with a tab that is open but busy or still loading `editor_tab_busy`, retryable, so the agent waits and calls again. The refusals' words about opening the editor follow the person's host setting, read at each refusal (the hosted app's "Agents may open the editor for me"): Ask first (the default) tells the agent to ask the person to open the link or bring the tab forward, or to ask permission before opening it itself; Allow, that it may open the link itself, in a tab in front; Never, to ask the person and not open or switch windows. It words `editor_tab_required` and `editor_tab_hidden` only: `editor_tab_busy` carries no link, and an autonomous agent account is refused with `editor_host_identity_required`. A server without a `sceneViews` host refuses `view_unavailable`; a session with no project, `no_project`; a photo crop the host cannot make, `photo_crop_unavailable`.

The answer is the picture plus the pose it was taken from, and which tab rendered it and when. A host that keeps the picture also answers its `viewId` (`SceneViewCapture.viewId`): those exact pixels, which a later call (a render of this view) names instead of taking the view again. The tool stays read-only: keeping a picture the host already took changes nothing a person sees. A picture is not a measure: sizes and counts come from the tools.

Views are planned on the site: a building's position and yaw move and turn the boxes of what stands under it, so a building away from the origin is looked at where it stands. A roof, or a roof level holding only roofs, frames its segments from its seat to its peak.

**Inside a room.** `interior: { zoneId }` stands the eye in a room (a zone) at a person's height (1.6 m above its floor, or `eyeHeight`), a step in from the corner farthest from what it looks at (`from` picks the corner on that side; a `target` is looked at), with a 75° field of view (`fov`), looking level across the room at its far wall. The floor is cut as for `levelId`, and the plan hands the host the level id and the room id (`roomId`), which only the note reads: `sceneViewNote` says the eye stands inside the room when it does. `position`, `elevation`, `from: 'above'` or `projection: 'orthographic'` keep the cut room seen from outside, framed on the room. `interior` takes one of `levelId` and `zoneId` (`interior_one_of`); a zone with no floor or outline is `interior_room_invalid`. The chat, the MCP and the hosted MCP share it through `sceneViewPlan`; `furnish_room` names it in its description and in the result for a room given by `zoneId`.

**Objects in a batch.** `run_batch` runs `add_object` calls. A compile is async and the operations are sync, so the host builds every add_object module first (`buildBatchObjects`, three compiles at a time, with the same compile its lone `add_object` uses) and hands the results to the batch in `AgentContext.batchObjects`; `addObjectInBatch` places each, with the receipt a lone call gives (`achieved` per object). `add_object` is in `INDEPENDENT_BATCH_TOOLS`: a module that fails (`script_failed`), a missing reason, an invalid input or a refused placement is that call's own report, whatever `onRefusal` says, and the other objects are applied. A refusal of another tool in the same batch still stops it and applies nothing. A host that built nothing answers `object_not_built` (the chat builds through `executeRunBatch`, the MCP through `registerOperationTool`'s `buildObject` host).

**Inside a floor.** `interior: { levelId }` looks into one floor. The plan checks the level (`interior_level_invalid`, also for a level holding only roofs and ceilings; `interior_hidden` for a hidden level or ancestor, a hidden site excepted, since it hides only its ground; `interior_transform_unsupported` for a tipped building) and that a target is on it and in the picture (`interior_target_elsewhere`, also for its roofs and ceilings), frames the floor from 55° above unless a target, an eye or a camera is given, and hands the host only the level id. The editor that renders it works out the rest from its own scene with `sceneViewInterior`: for that one render the other floors and this floor's roofs and ceilings are hidden, everything on the floor (walls, openings, furniture) and its shadows are cut at 0.65 of the storey height, its walls are drawn whole whatever the user's wall mode, and the user's solo and isolation are lifted on it. Everything is put back right after the render, so the live view does not change.

**Level presentation.** `presentation: { mode: 'solo', levelId }`, `{ mode: 'exploded' }` or `{ mode: 'stacked' }` captures the viewer's settled level arrangement, without changing the graph or saved viewer preferences. Solo preserves full-height walls, ceilings and roofs owned by that level, and keeps higher levels as shadow casters; it does not apply the interior cut. Exploded framing includes the shared level gap and explicitly classified retained roof bounds. Both surfaces carry this policy to the same snapshot renderer. `interior` and `presentation` cannot be combined; missing/hidden Solo levels and targets on another level are refused. The by-hand equivalent is the viewer's level mode and level selection.

## Checking the scene: `verify_scene`

One check for every surface: `verify_scene` (`verifyScene` in core) reports per level its content, role and the spaces its walls and separators enclose, then every problem it finds, each issue typed. It took over the MCP's `validate_scene`: every node field its schema rejects (the host's for a kind its bridge checks, else the registered kind's own, else core's) is a `schema_invalid` issue with its `nodeId` and `path`, all of them, and a hidden site is `site_hidden` (info). The checks that measure read each node with the defaults its schema fills (a level stored with no `children`), the stored node itself when it lacks none, so a host reading its own state by identity still finds it. A malformed node is left out of them, which could not read it, and the level holding it waits for the fix: it lists the node as `unread` and gets no finding read around it (a room open for the wall left out, a door off its wall), nor do the checks across levels (openings, furniture, wall and ceiling objects, registered checks), which read the scene without it, nor its building's stairs. A node of a kind no schema here knows (a plugin's, where the plugin is not loaded and the host does not check it) is no error: one `schema_unknown_kind` issue (info) per kind gives its count and a few ids. It took the room findings of the hosted Architect's `check_rooms` (`roomFindings`): a space the walls enclose with no zone over it (`space_no_room`), or with several rooms lying in it and no wall between them (`space_many_rooms`: the reconciler's "Room N" beside a zone drawn over it, a plan's rooms split by lines no wall draws; a mezzanine, or a zone no room, does not count); a room the walls and separators do not close (`room_not_enclosed`), a room being a zone with `spaceRole: 'room'`, and an automatic room the reconciler marked open when its walls stopped closing it counting as not closed, while a room a person declared open needs no walls; a generic zone walls of a room's height (2 m and up) bound along most of its outline is a room too, and gets the same finding as info, since it may be a courtyard; one garden walls bound, or no walls, is no room; a room with no name or only "Room" or "Zone" (`room_unnamed`, info). A store numbers a room for every enclosed space when it loads a scene and after each edit, so `space_no_room` reads a graph as stored or a level mid-edit. Their case table is `scene-check-cases.ts`. Issues with severity `info` are observations; `hasIssues` counts the rest.

## Furnishing follows a brief: `design_brief`

`design_brief` records the request as a brief: `axes` (the request read axis by axis: `action`, `size`, `pieces`, `openings`, `style`, `materials`, `dressing`, each bounded — the person's own words as `quote`, the reading in a short line, `pieces` as a `minimum` or `exact` — or open with a design statement of at least three words; an absent axis is refused `axis_missing`, a quote not in the person's message in the chat `axis_quote_not_in_request`, an open axis without its design `axis_open_without_design`; over MCP an axis quote is required and not compared, there being no message), the eighth axis `source` (`open`, `catalog`, `brand` with its `brand`, `existing`), a `vision` a `beyond` (the dressing, layer by layer: textiles, light, windows, walls, floor, plants, objects, small furniture, each pieces or `{ none: why }`; an open `dressing` axis owes pieces for 6 of the 8, `beyond_too_thin`, a bounded one owes none, and the dressing cannot be bounded by a quote inside a `pieces` quote read as a minimum, `dressing_bounded_by_minimum`; the result hands the pieces back as `dressing`, nothing checks them later; a brief stored as `fixed`/`open` lists, or with a string `beyond`, still reads), a `sourceQuote` for any source but `open` (the person's own words that set it: at least two words naming the brief's brand, the catalog or what is already there, from explicit English and French lists in `design-brief.ts`, `source_not_named`; the chat also checks it against the turn's message through `AgentContext.requestText`, `source_not_in_request`; over MCP only that second check is skipped). The stored brief reads without `beyond` (reading is tolerant, the tool's input is strict) and, for an open source, `asIs` (technical equipment only: sanitaryware, kitchen and laundry appliances, fixed services; each piece shown by `view_assets` earlier in the turn or session, `SessionRecord.viewed`, each with a reason; furniture is made: `brief_as_is_furniture`, `brief_as_is_not_viewed`). Core's `designBrief` echoes it with what it unlocks and hands it to the host as a session keep (`SessionKeep.designBrief`, replaced by the next brief, `null` takes it away); it changes nothing in the scene.

The gate is a fact of the furnishing tools, in core: `furnishingRefusal(tool, input, brief)` refuses `place_items`, `furnish_room`, `place_in_room`, `add_object` and `place_design` before a brief (`design_brief_required`); under an open brief it refuses the catalog's placements except the `asIs` pieces and all of `furnish_room`, which places a whole stock set (`brief_source_open`); a catalog, brand or existing source opens everything. `run_batch` is refused whole when one call is refused, whatever `onRefusal` says, before any call runs. Reading the catalog (`search_assets`, `view_assets`), rooms, walls, openings and finishes are never gated, and neither is an `add_object` that edits a standing object (`nodeId`). The operations of the gated tools refuse when the host lends `AgentContext.designBrief` (`null` while there is none, left out where the host does not gate); a host with an async step in front (the compile of an object) asks `furnishingRefusal` first.

The brief lives where the host keeps the agent's session (`SessionRecord.designBrief`): over MCP, the bridge's session (`briefInForce`), which a scene load or clear starts anew; a bridge that keeps no session gates nothing. The hosted chat keeps it in the thread's session for the turn (the chat clears it when a new user turn starts) and gates only the scene agent's calls.

## Finishes: `paint` and `search_materials`

`paint` gives surfaces a finish as the editor's Paint does, in one call and one undo step: the slots the editor's slot paint writes, a wall's faces through the same paint plan (`planWallPaint` in core, shared with the editor's wall paint), a roof's or a segment's `top`, `edge` or `wall` role field. `exterior` and `interior` resolve to a wall's faces from the rooms on its sides. A face is painted whole: its own slot, and an override in each room whose wall finish would otherwise show over it, as the editor's Paint writes a click on that room's face; painted parts (regions) keep their own finish and the result's `note` names them. A colour paints with the nearest library colour, and the result says how near. `search_materials` finds `library:<id>` refs by whole words (a short or common word is dropped), shade and surface, and names the words the library does not answer; a flat colour suits every `surface`.

A native material (an exact PBR finish) is kept as a scene material, reused when the scene holds one the material schema reads as equal. The operation returns it in `SceneChanges.materials`; a host writes it before the nodes that use it, in the same step. It needs the scene's materials in `AgentContext.materials`: the MCP lends them when its `SceneOperations` sets `supportsMaterialUpserts` and has `getMaterials`, and applies them as `upsert_material` patches (an internal op, not part of `apply_patch`'s schema). A host without them refuses a native material (`materials_unavailable`) and still paints library refs and colours. `get_node` returns the scene materials a node's finishes use when the host lends them.

## Emptying a project: `clear_scene`

A write that would leave a populated project empty is far more often an accident than an intent, so a store may refuse it: the save options carry `allowSceneWipe`, and without it a guarding store throws `SceneWipeBlockedError` (a `SceneInvalidError`). Live sync answers that refusal as `scene_wipe_blocked` with `mutationApplied: false` and loads the stored scene back into the session, so the agent's next write builds on the project as stored; when the stored scene cannot be read back, it says to call `load_scene` first.

`clear_scene` is the only way to empty a project on purpose: it resets the scene to the host's default scaffold (a site, a building, one level), keeps the project's installed plugins, clears the undo history, and saves with `allowSceneWipe`. Its `reason` says what the person asked. The by-hand counterpart is the hosted editor's **Clear the project**, offered on the notice when a save is refused as a wipe. A store with no wipe guard (the local SQLite store) saves either way.

## Converting a whole design: `author_scene`

Item slots keep their authored colours as exact materials. Opening `color` paints the door’s panel and frame or the window’s frame; `frameColor` overrides the frame (default: `color`). Scripted openings keep their declared `type`; only `style` is ignored. Wall-hosted items keep the bottom centre’s outward distance from the nearest face; a point inside the wall body moves to the face and is reported in `defaults`.

A frontier model builds a richer room or house as free three.js than through the scene tools one call at a time, and the test that settled it (four fresh agents converting the same flat from a contract and a gate report alone, none of them using the reading helpers offered) also settled the division of work: **the agent reads its own module, Pascal writes.** `author_scene` (`core/agent-tools/author-scene.ts`, operation in `core/agent-operations/author-scene.ts`; registered on the MCP first and not yet in `AGENT_TOOL_CONTRACTS`, since the hosted chat's agent cannot run its own program until its sandbox can emit the payload: a reviewed `gap` in the parity test) takes a conversion payload, levels with walls (a colour for both faces or `colorLeft` / `colorRight` for one: the left, looking from start to end, is the wall's front, role `a`; a `skirting` with height, depth and colour) and their openings (`type` as `DoorType` / `WindowType`, `style` as the door and window style presets, `leaves`, or `code` for a module the host compiles like an item's, keyed `<wallId>/<index>`), rooms by seed with a floor material and regions and an optional `floorCode`, slabs, columns, railings, items as authored-object modules placed at their bottom centre (hosted on another item when they rest on it, or on a wall when `host` names one: a wall-side item on the face nearest its point, as `place_items` writes one), lights, and writes native nodes: `WallNode`s, `DoorNode`/`WindowNode`s on their wall (`doorTypeFields` / `windowTypeFields`, `doorStyleLook` / `getWindowStyleOverrides`, the handle opposite the hinge, a scripted opening's `source` and `slots` as `add_door` with code writes them), zones through Pascal's own room derivation (`migrateRoomZones`) with the payload's names and finishes, floors and ceilings through `reconcileSceneStructure`, each wall's skirting through `setWallSkirting` once the rooms exist (on the faces a room stands on, its colour through the same exact materials; a refusal is a `skirting_refused` defect), items through `addObject`, lights as light effects on their fixture (or a compiled 60 mm × 8 mm ceiling point hosted on its room’s ceiling when no fixture is given, or the nearest item on the level outside rooms: Pascal keeps lights inside objects) in the host's frame, paint through `paint`. A hex colour is one exact scene material per distinct colour across the payload (`resolveInlinePaintMaterial`, roughness 0.9, metalness 0, named by the hex), reused by item slots, opening panels and frames, walls, floors, regions and slabs alike; a host without scene materials gets the nearest library colour and a `defaults` sentence saying so. Ids derive from the payload's hash, so the same payload writes the same scene.

The policy is accept and report: everything valid is written, every defect comes back by the payload's own id with a code, and its join rule corrects wall ends (an end within 0.3 m of another wall's centerline snaps onto the line, extending the short end rather than sliding the wall it meets), listed per wall. The report also says what Pascal filled in or dropped (`defaults`, one sentence per fact: windows with no type written fixed, a door's handle set opposite its hinge, a style dropped on an operable window, a ceiling point for a light without a fixture) and what it wrote but doubts (`warnings` with a code: `thin_slab` under 2 cm, `many_slabs` over 20 on a level, `many_regions` over 24 in a room, since regions are fixed polygons that do not follow a resize). One structural defect refuses the node: `slab_over_wall`, a slab over a wall's footprint on its level with its top above half the wall's height, which would lift the wall onto it (an acceptance run wrote 43 twelve-millimetre "wall cap" slabs at 2.662 m). Pascal builds a wall's cap, the floor plate and the ceiling itself; the skill tells the agent to fold a module's caps, underlays and planks into the wall, the floor finish and the room. A scene already holding a conversion is refused unless `replace` is set; replacing deletes the levels and writes the payload's. The host also compiles the candidate ceiling-point modules listed by `authorSceneCeilingPoints`; after reconciliation the operation uses the ceiling belonging to the room containing each light’s plan position. The host compiles each item's module first (the MCP on its server through the `GeometryScriptHost`, the chat in its worker) and passes the results keyed by item id; a failed compile is a `compile_failed` defect. A room's `floorCode` is its floor script (`authored-objects.md`, "Room floor scripts"): core cannot compile, so the operation lists the rooms that have one by zone (`authorSceneFloorScripts`), and the host, once the write is applied, reads each room's floor (`floorScriptInputs`), compiles the module for it through the `GeometryScriptHost` with `inputs` (the hosted server's editor tab and its server compile carry them too) and writes it with `setRoomFloorScript`, counting `floorScripts`; a failure is a `floor_script_failed` defect and the room keeps its `floor`. A wall's `faceLeft` / `faceRight` (face `a` / `b`) and a room's `wallCode` (on every face its floor meets, the spans `setWallSkirting` runs along, a wall's own module winning) are face scripts (`authored-objects.md`, "Wall face scripts") wired the same way: `authorSceneFaceScripts` lists them by face once walls and zones exist, the operation reporting a face no room looks into as `no_face` (and a face two rooms' `wallCode`s claim as a `face_shared` warning), and the host reads each face (`wallFaceScriptInputs`, with `toHeight`), compiles it as a `wall-face` and writes it with `setWallFaceScript`, counting `faceScripts`; a failure is a `face_script_failed` defect named `<wallId>/<face>` and the face keeps its paint. `get_source` reads a room's floor script by its zone id, and a wall face's script by the wall's id and `face` (`authored-objects.md`, "Wall face scripts"). The MCP tool (`mcp/tools/author-scene.ts`) also keeps the design's module and the agent's program as scripts of the scene and records the payload (without the items', openings', floors' and faces' code, which are their own artifacts) and the report on the building's `metadata.authorScene`, then answers the gate report with `verify_scene`'s issues: replay is the stored payload through the same operation, with no model.

What the converting agents asked of `verify_scene` is in the same PR: an item hosted by another item is read through its host (`item-space.ts`), a thing resting on its host is stacked, not colliding, a rug or a pendant does not block a door, and a door's keep-out is the full clear depth on its swing side and a walkway on the other.
